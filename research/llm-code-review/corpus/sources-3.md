# Sources — Skeptic / critical-methodologist perspective

Canonical question: How effective are LLM-generated code review comments at finding real defects compared to human reviewers?

Focus: replications and “LLM hype” critiques; false positives in automated review; style/nit comments inflating “finding” rates; failure cases and metric pitfalls (BLEU/EM vs real defects; acceptance ≠ defect detection; gold-set incompleteness).

---

## S1. Benchmarking and Studying the LLM-based Code Review (SWR-Bench)
url: https://arxiv.org/html/2509.01494v1
published: 2025-09-01 (arXiv 2509.01494v1)
type: primary
origin: independent
claims:
  - claim: On a realistic PR-level benchmark of 1000 verified GitHub PRs, SOTA automated code-review techniques plus SOTA LLMs are not ready for real-world deployment; top F1 is only ~19%.
    quote: "The results in Table III show that SOTA ACR techniques, when paired with SOTA LLMs, are not yet ready for real-world code review deployment based on their performance on SWR-Bench. For instance, the top-performing combination, PR-Review leveraged with Gemini-2.5-Pro, achieved an F1 score of only 19.38%."
  - claim: Low precision (high false-positive rates) is the main limiter; four of five ACR techniques had overall precision below 10%.
    quote: "A primary factor limiting higher F1 scores for all techniques is their low precision, indicative of a high false positive rate. This issue is more severe for other four ACR techniques, all of which exhibited precision scores below 10%."
  - claim: High FP volume forces developers into costly verification, undermining practical adoption even when some real issues are found.
    quote: "This implies that while these ACR techniques can identify some valuable issues (or “change-points”), their overall effectiveness is severely undermined by an excessive number of false positives. Consequently, developers would need to invest considerable additional effort in verifying the validity of the generated reports, hindering practical adoption."
  - claim: Prior ACR benchmarks often mis-evaluate tools by using fine-grained units, missing project context, and relying on BLEU/Exact-Match or biased LLM ratings rather than issue coverage.
    quote: "metrics like BLEU primarily measure textual similarity, while the reliability of LLM ratings is often questioned due to potential inherent biases; both approaches have been shown to be severely inadequate in assessing whether the crucial issues are truly identified in code review comments"

## S2. Studying Quality Improvements Recommended via Manual and Automated Code Review
url: https://arxiv.org/html/2602.11925v1
published: 2026 (ICPC ’26; arXiv HTML 2602.11925v1)
type: primary
origin: independent
claims:
  - claim: ChatGPT-4 recommends ~2.4× more changes than human reviewers on the same PRs but matches only ~10% of human-identified quality issues.
    quote: "We show that while, on average, ChatGPT tends to recommend a higher number of code changes as compared to human reviewers (∼2.4× more), it can only spot 10% of the quality issues reported by humans."
  - claim: Only ~40% of ChatGPT’s extra (human-unmatched) comments are judged meaningful; the rest inflate “finding” volume without proven value.
    quote: "However, ∼40% of the additional comments generated by the LLM point to meaningful quality issues."
  - claim: Authors conclude LLM review is complementary noise-heavy assistance, not a replacement that saves review time.
    quote: "in its current state, DL-based code review can be used as a further quality check on top of the one performed by humans, but should not be considered as a valid alternative to them nor as a mean to save code review time, since human reviewers would still need to perform their manual inspection while also validating the quality issues reported by the DL-based technique."
  - claim: Exact match / BLEU-style automated metrics are inadequate for judging comment quality because the same defect can be worded differently.
    quote: "EM predictions (i.e., the comment generated by ChatGPT is exactly the same as the one posted by a human reviewer) might not be the best option for this task, since the same concept can be expressed using completely different wordings, thus also invalidating metrics such as BLEU."
  - claim: Providing broader PR context to ChatGPT did not improve matching of human issues (it lowered match rate), challenging “just add more context” narratives.
    quote: "providing a broader context to ChatGPT (e.g., all files impacted in the PR) actually lowers the percentage of cases in which it is able to spot the same quality issues identified by humans."

## S3. Impact of LLM-based Review Comment Generation in Practice (RevMate @ Mozilla & Ubisoft)
url: https://arxiv.org/html/2411.07091v1
published: 2024-11-11 (arXiv 2411.07091v1)
type: primary
origin: independent
claims:
  - claim: In a live mixed open-/closed-source deployment (>587 patches, ~1.6k generated comments), only ~7–8% of LLM-generated comments were accepted by professional reviewers.
    quote: "Based on more than 587 patch reviews provided by RevMate, we observed that 8.1% and 7.2%, respectively, of LLM-generated comments were accepted by reviewers in each organization, while 14.6% and 20.5% other comments were still marked as valuable as review or development tips."
  - claim: Refactoring/style-oriented comments are accepted far more often than functional (defect-oriented) comments—so raw “finding” or acceptance rates can be inflated by non-defect nits.
    quote: "Refactoring-related comments are more likely to be accepted than Functional comments (18.2% and 18.6% compared to 4.8% and 5.2%)."
  - claim: Most generated comments are classified as functional issues, yet those have the lowest acceptance—suggesting false or low-value defect claims dominate volume.
    quote: "for Mozilla and Ubisoft respectively, 79.2% and 84.9% of generated comments are classified as functional issues, and 15.8% and 14.5% as refactoring-related comments. Furthermore, we found that refactoring-related comments have higher acceptance ratios than functional comments (18.2% and 18.6% compared to 4.8% and 5.2%)."
  - claim: Prior lab evaluations relying on BLEU/Exact Match understate the need for live reviewer acceptance studies.
    quote: "thus far these have only been evaluated using textual metrics such as BLEU score and Exact Match, which are imperfect as they do not capture the actual impact and synergy the approach can have on reviewers"

## S4. Evaluating Large Language Models for Code Review
url: https://arxiv.org/html/2505.20206v1
published: 2025-05-26 (arXiv 2505.20206v1)
type: primary
origin: independent
claims:
  - claim: Even with problem descriptions, GPT-4o correctness classification accuracy is only ~68.5% on mixed correct/incorrect code; Gemini is ~63.9%—too weak for unsupervised merge gating.
    quote: "With problem descriptions, GPT4o and Gemini 2.0 Flash correctly classified code correctness 68.50% and 63.89% of the time, respectively, and corrected the code 67.83% and 54.26% of the time for the 492 code blocks of varying correctness."
  - claim: Authors conclude full automation is unreliable due to substantial error and regression rates.
    quote: "Firstly, the results indicated that LLMs would be unreliable in a fully automated code review environment."
  - claim: LLM suggestions can worsen already-correct code (regressions), including rates that roughly double without problem descriptions.
    quote: "In terms of regressions, we observed that up to 24.80% of correct code blocks received incorrect code suggestions. The regression rates were higher, and even doubling, without the problem descriptions."
  - claim: Performance flips across datasets (mixed vs HumanEval ground-truth), so headline scores are not stable across code types.
    quote: "The correctness accuracy results contradicted the mixed dataset findings as seen in Figure 8. Gemini outperformed GPT4o with 66.67%, compared to GPT4o’s 42.07% with problem descriptions."

## S5. Code Review Automation: Strengths and Weaknesses of the State of the Art
url: https://arxiv.org/html/2401.05136v1
published: 2024-01-10 (arXiv 2401.05136v1)
type: primary
origin: independent
claims:
  - claim: Quantitative “% correct on test set” scores for review automation hide whether models only hit low-hanging fruit (e.g., formatting) rather than real defects.
    quote: "knowing that an approach is able to correctly address a reviewer’s comment in 10% of cases is of little value without knowing what was asked by the reviewer: What if in all successful cases the code change required to address the comment was just the removal of an empty line?"
  - claim: ~25% of inspected train/test dataset instances were mining noise that undermines reported performance and evaluation validity.
    quote: "we found that ∼25% of the instances in the inspected datasets are the result of data extraction errors possibly undermining the techniques’ performance and questioning the validity of the evaluation performed on the test set."
  - claim: ChatGPT struggles at the code-to-comment task relative to specialized techniques—undercutting “general LLM already solves review” claims.
    quote: "we compared the three subject approaches with ChatGPT, showing that, while the latter represents a competitive solution for the code & comment-to-code task, it suffers in the code-to-comment task."
  - claim: Models fail systematically on complex multi-component changes because their “view” is limited to a single function/diff hunk.
    quote: "the experimented techniques struggle when they need to recommend (code-to-comment task) or implement (code & comment-to-code task) complex code changes spanning across several code components. This is due to the “view” they have of the code base, usually limited to a single function or diff hunk submitted for review."

## S6. Code Review Bench: Towards Billion Dollar Benchmarks (Martian)
url: https://withmartian.com/post/code-review-bench-v0
published: 2026-02-26
type: primary
origin: independent
claims:
  - claim: No evaluated code-review tool found more than 63% of known issues—even the best still misses ~1/3 of bugs on the gold set.
    quote: "Equally exciting: no tool found more than 63% of the known issues. The best tool still missed a third of the bugs. The verifier is far from solved."
  - claim: Offline gold sets are systematically incomplete; comments scored as false positives can be real issues missing from ground truth—distorting precision and recall rankings.
    quote: "When we ran tools against those datasets, some of the comments we initially scored as false positives turned out to be real issues the gold set didn't include. [...] Every tool's precision is being understated (real finds are scored as false positives) and every tool's recall is being overstated (the denominator of \"bugs that exist\" is too small). The magnitude of this effect is large enough to change rankings."
  - claim: Online (developer behavior) and offline (controlled gold-set) benchmarks disagree—static lab rankings should not be trusted alone.
    quote: "The most important finding is that the online and offline benchmarks disagree. This is what we expected, and it's why we built both."
  - claim: High-volume/noisy tools may look worse on incomplete gold sets while still getting real developer action—F1 without behavioral checks can mislead.
    quote: "The offline data seems to show a clear pattern: tools that comment more have lower precision. But the online data complicates that story. Coderabbit has the highest recall in the online data (0.54) and the most PRs reviewed (5,035). Developers are acting on its comments at a substantial rate despite the volume."

## S7. Automated Code Review In Practice (industry case study @ Beko)
url: https://arxiv.org/html/2412.18531v2
published: 2024-12-28 (arXiv 2412.18531v2)
type: primary
origin: independent
claims:
  - claim: Despite 73.8% of bot comments labeled “Resolved,” mean PR closure time increased substantially after deploying the LLM review bot (overall ~5h52m → ~8h20m).
    quote: "73.8% of automated code review comments were labeled as resolved. However, the overall average pull request closure duration increased from five hours 52 minutes to eight hours 20 minutes, with varying trends observed across different projects."
  - claim: Authors list concrete failure modes: faulty reviews, unnecessary corrections, and irrelevant comments.
    quote: "it also led to longer pull request closure times and introduced drawbacks such as faulty reviews, unnecessary corrections, and irrelevant comments."
  - claim: About one quarter of bot comments were not acted on as “Won’t Fix”/“Closed”—developer time spent on noise.
    quote: "The results from the comment resolution labels show that 26.2% of the tool comments were not acted upon as they were labeled with \"Won't Fix\" or \"Closed\". These comments could be too trivial, unrelated or not a problem for the context of the pull request."
  - claim: Human review volume did not drop significantly—automation did not replace human defect-finding effort.
    quote: "Overall, human reviewers left an average of 0.31 comments per pull request before deploying CodeReviewBot, which decreased to 0.28 afterward [...] The Poisson regression analysis indicated that this overall decrease was not statistically significant"
  - claim: Practitioners reported suggestions outside task scope and “mistakes” that were not mistakes—classic false-positive / nit inflation.
    quote: "One respondent in the general opinion survey said, \"It also makes suggestions that fix code blocks that are not in the scope of the task,\" and another said, \"Sometimes the mistakes it thinks it finds are not mistakes at all.\""

## S8. Reducing False Positives in Static Bug Detection with LLMs: An Empirical Study in Industry
url: https://arxiv.org/html/2601.18844v1
published: 2024 (venue year on page; arXiv HTML 2601.18844v1; data Sep 2024–Jun 2025)
type: primary
origin: independent
claims:
  - claim: Even hybrid LLM+static approaches still fail on industrial false-alarm reduction for long contexts, cascaded constraints, and weak semantic understanding—limits that also apply when LLMs author review comments about defects.
    quote: "we perform bad case analysis to identify the limitations of LLMs when applied to enterprise-scale bug detection, such as handling bugs of long code contexts, reasoning complex cascaded constraints, and insufficient semantic understanding."
  - claim: Explicit industrial failure modes for LLM reasoning over bug alarms.
    quote: "Specifically, LLMs exhibit (1) limited effectiveness in handling long code contexts, (2) difficulty reasoning complex cascaded constraints, and (3) insufficient semantic understanding."
  - claim: Enterprise static warnings themselves are extremely FP-heavy (>90% when counting discarded incomplete cases), so treating “warnings reviewed by LLM” as defect discovery without careful labels confounds evaluation.
    quote: "When accounting for these discarded cases, the false positive rate of static warnings is higher than 90%."
  - claim: LineVul-style models can look accurate by classifying almost everything as false positive—accuracy without balanced defect metrics is a methodological trap.
    quote: "Although Linevul reports a seemingly high accuracy of 0.76, this result stems from its tendency to classify all warnings as false positives. Since our dataset contains a large proportion of false positive cases, this bias inflates its accuracy but undermines practical value."

## Notes on independence / derivatives
- S1–S5 and S7–S8 are peer-oriented research papers (arXiv/HTML primary). S6 is the original methodology announcement from the benchmark authors (not a vendor reblog of someone else’s study).
- Vendor blog posts that only restate Martian leaderboard numbers (CodeRabbit/cubic marketing) are **not** listed—they are derivative of S6-style public leaderboards.
- S4 and S7 share an author (Cihan) and institution but report **different** studies (lab HumanEval-style evaluation vs multi-month industrial deployment); treated as independent evidence, not reprints.
